The signed-BPF field trip

Ten stops, one signature

Each panel is a close-up of the map above. The pictures are metaphors; the names, paths, hooks and numbers in them are the real ones from shirudo’s documentation.

1 Stop 1 · Workshop

The workshop: build and sign

The operator writes BPF C and runs shirudo bpm build. A separate helper, shirudo-build, compiles it with clang 23 for instruction set v4, and libbpf’s gen_loader turns the object into a loader: a small BPF_PROG_TYPE_SYSCALL program whose data carries the payload programs. The helper signs loader_insns ‖ data with the ML-DSA-87 private key as a detached CMS signature.

Field noteOne signature covers every instruction that ends up attached, because the payload rides inside the signed data. The operator keeps no state about targets, so losing its host loses nothing but the key.

2 Stop 2 · Registry

The registry: publish

shirudo bpm push publishes versioned packages to an OCI registry, and a signed index names each package by digest. shirudo bpm tree append adds operations to the upatch tree, an append-only, ordered list where each operation adds or deletes one upatch for the targets its selector matches: architecture, kernel release, kernel build ID, kernel config values or node labels.

Field noteEach tree generation carries a detached CMS signature and names the one it replaces. The registry is trusted with nothing: the target checks every object’s own signature before acting on it.

3 Stop 3 · Pull

The roof pump: pull, never push

Nothing connects into a target. systemd timers start one-shot commands, bpm repo update, bpm upgrade and bpm tree sync, that fetch, verify and load. tree sync verifies the publication against the active config’s signer set, evaluates each new operation’s selector on this target and applies the matching ones in sequence order.

Field noteNo daemon, no listening socket. A udev rule starts upatch reconcile when a network device appears, to attach XDP upatches. No target command starts another program.

4 Stop 4 · Workbench

The workbench: read once, check

shirudo upatch load reads the file into memory once, and every later step takes its bytes from that read. It refuses the artifact unless the signed name equals the header name and payload_sha256 equals SHA-256 of loader_insns ‖ data, and it holds the register lock from before it touches the pins until the record is appended.

Field noteThe worker carries runtime authority: a mark a task gets only by executing a file from the dm-verity runtime image upstairs. The guards ask for that mark, not for a user ID or a capability.

5 Stop 5 · Gate

The gate: bpf() meets lsm/bpf

Every bpf() call is checked by lsm/bpf at entry. Calls from userspace arrive with kernel false and are filtered: shirudo’s own need runtime authority, and a program load must be a SYSCALL program with a signature. Root cannot load BPF of its own, create maps or attach links, even with CAP_SYS_ADMIN.

Field noteCalls made from inside a verified loader reach the hook with kernel true and are allowed. That one argument tells the operator’s code from root’s.

6 Stop 6 · Frozen map

The ice block: __loader.map

The kernel can only verify a signature over data it has seen, so the data goes first, into a one-element array map. shirudo sets excl_prog_hash to SHA-256 of the loader’s instructions, so the verifier refuses to bind the map to any other program, then writes the data and freezes the map.

Field noteThe kernel refuses a signed load whose bound map is not an array, not frozen, has active writers or is not exclusive.

7 Stop 7 · Verifier

The verifier and the vault

BPF_PROG_LOAD passes the map in fd_array. Inside bpf_check() the kernel binds it and verifies the signature over the loader’s instructions followed by the map’s frozen value against the .bpf keyring. lsm/bpf_prog_load then admits the program only on a good verdict from the right kind of keyring.

Field noteinit enrolled the operator’s certificate in .bpf at boot and sealed the ring. A live signed config can revoke an enrolled key and purge its upatches, but it cannot enroll a new one.

8 Stop 8 · Loader & pins

The loader and the pinboard

A test run starts the loader. Its own bpf() calls create the upatch’s maps and load its programs, and the verifier checks each payload program as usual. shirudo then attaches each program, compares the link the kernel reports with the signed attach metadata, refusing with attach_scope_mismatch when they differ, and pins it under /run/shirudo/bpffs/upatches/<name>/.

Field noteThe pins keep the links attached after the one-shot command exits. A copy of the artifact goes to /var/lib/shirudo/upatches/ so the next boot can restore it.

9 Stop 9 · Register

The ledger in the TPM

The load event is extended into the measurement register under a domain-separated tag and the eventlog takes the record; a failed copy or a refused extension undoes the load. The register is an NV extend index, 0x01818E00 by default, that behaves like a PCR: each write replaces it with SHA-256 of the old value followed by the event, and it clears at every TPM reset.

Field noteEvery extend needs a signature from a writer key made inside the TPM at boot, and lsm/tpm_command refuses an NV_Extend of the index to every task without runtime authority. The first write works only while PCRs 9 and 11 hold the values init read, which is why init binds it from the initrd.

10 Stop 10 · Evidence

Home again: evidence, checked offline

The operator picks a fresh nonce and runs shirudo attest --nonce=<hex> on the target. The TPM signs a quote over PCRs 0–7, 9 and 11–15 and a certification of the register with its attestation key, and the command adds this boot’s eventlog records. On the operator host, shirudo attest verify checks the nonce, the signatures and the pinned key, the register’s name, that the records replay to the certified value and that PCR 9 carries the anchor, without a TPM.

Field noteshirudo writes the evidence document; how it reaches the operator is up to the administrator, since shirudo has no transport of its own. shirudo attest predict computes the expected register from the certificates and artifacts the operator already has.

Other passengers

The packages under upatches/ in this tree. Most are BPF and take the signed-loader path above; the Java agents take a weaker one.

BPF

kernel-cve

Upatches aimed at single kernel CVEs. Two refuse the path to a bug (AF_ALG sockets and zero-copy splice into them, CVE-2026-31431); three count the inputs that reach one (e1000 TBI frames of length 0, netem packets with an empty linear head, RPL routing headers whose n + 1 exceeds 127).

BPF

kernel-obs

Host observability: executed programs, network peers and listeners, DNS answers, privilege transitions and access to credential and persistence files. Every hook observes and nothing enforces. Each table lives in one BPF arena that the export drains.

BPF

app-sandbox

Puts applications in sandboxes that limit what they execute, where they connect and which files they write. It ships sandboxes for Apache httpd and PHP-FPM that keep a web app from rewriting the PHP it serves or starting other programs.

Java agent

java-base64 · java-sql-inj

Signed jars that guard JVM code: one rejects the input shape behind CVE-2026-114938 in Base64$Decoder.decode0, the other blocks structural SQL injection in JDBC statements. A JVM loads the jar, not the kernel, so its signature is checked in userspace and it reaches only JVMs started with shirudo’s JAVA_TOOL_OPTIONS. It is a mitigation inside the application, not a boundary against root.

One CVE, worked end to end

The kernel-cve packages above name CVE-2026-31431 twice. Here is why one flaw ships with two different shields, and what a shield has to deny to actually close it rather than just look closed.

The flaw · crypto/algif_aead

A cleanup that scrubs the wrong pages

When an AEAD operation over an AF_ALG socket hits its copy-failure path, the kernel writes back into the source scatter-gather pages it was reading from. That is harmless when the socket owns those pages: an ordinary sendmsg copies the caller’s bytes in, so the pages are the socket’s own. It corrupts memory the socket does not own only when a zero-copy splice (MSG_SPLICE_PAGES) has aliased foreign pages into the socket’s send list first. So the bug has exactly one precondition — foreign pages on the send list — and only the splice path puts them there.

Shield A · blunt

Refuse the whole subsystem

lsm/socket_create -EPERM

SEC("lsm/socket_create")
if (family == AF_ALG)   /* 38 */
    return -EPERM;

No AF_ALG socket opens at all, so the vulnerable code is simply never reached. The cost is that it also removes every other use of the kernel’s crypto through sockets — aead, skcipher, hash, rng — so this is the shield for a host that has no need of socket crypto.

Shield B · precise

Refuse only the one dangerous send

lsm/socket_sendmsg -EACCES

SEC("lsm/socket_sendmsg")
if (BPF_CORE_READ(sock, sk,
      __sk_common.skc_family) != AF_ALG)
    return 0;
if (msg->msg_flags & MSG_SPLICE_PAGES)
    return -EACCES;

The socket still opens and every copying use keeps working; only a MSG_SPLICE_PAGES send into an AF_ALG socket — the single way to alias foreign pages in — is refused. It reads the family and the flag from the generic struct sock and struct msghdr, which carry BTF, so it is CO-RE and rides from one kernel to the next.

Why one hook isn’t enough

Deny the precondition, not a symptom

Picture a shield that tried to catch the bug where it fails — say, keyed on “an AEAD decrypt that returns an error.” It would be easy to never meet on those terms. The same copy-failure writeback is reachable through skcipher, hash and rng as well as aead, and on the encrypt side as well as decrypt. Worse for the defender, the operation and the algorithm live in the crypto module’s private af_alg_ctx, which carries no BTF, so a CO-RE shield cannot even read them without hard-coded offsets that shatter on the next kernel build. A shield pinned to one symptom is a shield you walk around by changing algorithm or direction.

That is why the shield that holds does not chase the symptom at all: it denies the one precondition every variant shares — foreign pages aliased in by a zero-copy splice — which lives in the generic structs a shield can read, and which no choice of algorithm or operation changes. Shield A denies it by removing the socket; Shield B denies it by removing the splice. The honest costs sit right next to the shields: A breaks legitimate crypto, and B trusts that MSG_SPLICE_PAGES into an AF_ALG socket is the only route to foreign pages on the send list. The operator chooses per host instead of pretending one answer fits every machine.

Watching, not enforcingA third program in the same package only observes: it marks a socket when a splice aliases foreign pages into it, then counts the marked sockets whose aead op later fails — the exact foreign-page writeback — against every aead op as the denominator. It blocks nothing; it tells the operator whether the path is actually being taken on this host.

Four quiet ways out

kernel-obs writes down who talked to whom — peer, port, bytes, per interval, and the names DNS resolved — and never records a payload. A metadata-only observer can record all four of these channels and flag none: the blind spot is not what it can’t see, it’s what it doesn’t interpret. It’s not magic; it’s encoding. (A localhost demonstration against a model of the documented telemetry, not an attack on a live deployment.)

Every morning: init runs twice

BPF programs do not survive a reboot, so each boot starts the register from zero and loads the archived upatches again.

In the initrd

shirudo-initrd.service

  1. Read the bootstrap settings the UKI authenticates and run the pre-flight: BPF LSM, signed-loader ABI, .bpf keyring, TPM.
  2. Bind /var/lib/shirudo and mount the private tmpfs and bpffs under /run/shirudo.
  3. Map the runtime image with dm-verity, check its root hash, then select and verify the config image.
  4. Enroll and seal the .dm-verity and .bpf keyrings and label the state.
  5. Attach the guards, restore the archived upatches and bind the register while PCRs 9 and 11 hold the policy values.
leave-initrd moves PCR 11; mounts and pins under /run cross over

In the root file system

shirudo.service

  1. Start the binary from the verified runtime image.
  2. Check what the initrd run left behind.
  3. Adopt its pending record from /run/shirudo/eventlog.pending. A re-run of init adds no register event.
